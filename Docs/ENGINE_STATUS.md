# Состояние движка LEN — краткая документация

## Обзор

LEN — экспериментальный игровой движок на C++ с минимальной подсистемой рендеринга и обработки ввода. Проект содержит
основу для работы с мешами, шейдерами, простую компонентную модель и демонстрационные объекты.

## Текущая функциональность (реализовано)

- Рендеринг:
    - Создание шейдерных программ через GraphicsAPI (например, вызовы вида CreateShaderProgram).
    - Поддержка простого вершинного формата (позиция + цвет).
    - Индексированные меши: классы для хранения вершин и индексов, привязка VertexLayout.
    - Материалы, которые хранят шейдерную программу и используются MeshComponent для отрисовки.
- Сцена и объекты:
    - GameObject с трансформацией и возможностью добавления компонентов.
    - Простейшая компонентная система: MeshComponent привязывается к объекту и отрисовывает меш.
- Ввод:
    - InputManager с возможностью опроса клавиш (IsKeyPressed) и кнопок мыши.
    - Поддержка отслеживания позиции мыши (старой и текущей) для вычисления дельты движения.
    - Тестовый объект умеет реагировать на W/A/S/D и стрелки для перемещения.
- Интеграция:
    - GLFW используется для создания окна и контекста OpenGL.
    - Синглтон-объект Engine для централизованного доступа к подсистемам (графика, ввод и т. п.).

## Последние изменения (фикс)

- Исправлена опечатка в макросе `COMPONENT` в `Engine/Source/Core/scene/Component.hpp` (`ovveride` → `override`).
- Исправлена структура макроса `COMPONENT`: убрана лишняя закрывающая скобка и корректно закрывается пространство имён
  `LEN`.
- Добавлена пропущенная точка с запятой при использовании `COMPONENT` в `CameraComponent.hpp`.
- Исправлены критические ошибки ввода и управления камерой:
    - `InputManager::isMouseButtonPressed` теперь возвращает состояние из `m_mouseButtons` (было возвращение из
      `m_keys`).
    - `Engine::mouseButtonCallback` теперь вызывает `SetMouseButtonPressed(...)` (ранее — `SetKeyPressed`).
    - `Engine::mouseCursorPositionCallback` корректно сохраняет старую позицию перед обновлением текущей позиции
      курсора.
    - В `Engine::Run()` исправлено обновление старой позиции мыши: теперь старое = текущее в конце кадра.
    - В `PlayerControllerComponent::Update` проверка нажатия мыши заменена на
      `isMouseButtonPressed(LEN::Key::MouseLeft)` (раньше некорректно делался static_cast от GLFW константы).

## Что это исправляет

- Камера теперь корректно реагирует на движение мыши при зажатой левой кнопке: вычисляется дельта (current - old) и
  применяется к повороту объекта-камеры.
- Мышиные клики правильно помечаются в отдельной структуре состояний кнопок мыши, а не смешиваются с состоянием клавиш.

## Как протестировать (коротко)

1. Собрать проект (Windows/MSVC, пример для PowerShell + Ninja):

    ```powershell
    cmake -S . -B cmake-build-debug -G "Ninja"
    cmake --build cmake-build-debug --target LENApp -j 8
    ```

2. Запустить созданный рантайм (LENApp).
3. В окне приложения: зажать левую кнопку мыши и двигать мышью — камера должна вращаться соответственно.
4. Если дергается/слишком быстро/медленно — отрегулируйте чувствительность в `PlayerControllerComponent.hpp` (параметр
   `m_sensitivity`).
5. Для режима FPS можно включить захват курсора: в `Engine::Init` или из приложения вызвать
   `glfwSetInputMode(window, GLFW_CURSOR, GLFW_CURSOR_DISABLED)` при желаемом входном режиме.

## Ограничения и дальнейшие шаги

- Среда сборки: у некоторых разработчиков могут возникать ошибки C1083 (отсутствуют системные заголовки `<string>`,
  `<array>` и т.д.). Это признак некорректной установки MSVC/Windows SDK или настроек окружения (надо запускать из
  Developer Command Prompt for VS или настроить CLion на MSVC правильно).
- GLEW и GLU: `glew.h` ожидает `GL/glu.h` — убедитесь, что соответствующие заголовки доступны в SDK, либо используйте
  чужой загрузчик OpenGL (glad) для уменьшения зависимостей.
- Возможность улучшений:
    - Захват курсора в FPS-режиме (GLFW_CURSOR_DISABLED) при зажатии ЛКМ.
    - Не умножать mouse delta на deltaTime (обычно вращение мышью не завязано на fps) — это поведение можно адаптировать
      в `PlayerControllerComponent`.
    - Добавить атомарность/мьютексы для InputManager, если планируется доступ из других потоков.
    - Добавить unit-тесты для InputManager и PlayerController логики.
